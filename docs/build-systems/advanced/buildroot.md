# Buildroot

## What Problem Does This Solve?

Buildroot builds complete embedded Linux systems with a simpler model than Yocto/OE. It is useful for fast BSP prototypes, small products, recovery images, factory tools, and learning root filesystem construction without the full OpenEmbedded metadata stack.

## Core Concepts

- Buildroot defconfig
- packages
- external tree
- toolchain backend
- rootfs overlay
- post-build script
- post-image script
- filesystem image
- board directory

## Mental Model

```text
Buildroot defconfig
-> toolchain
-> packages
-> rootfs skeleton and overlays
-> kernel/U-Boot if enabled
-> filesystem and disk images
```

Buildroot is configuration-driven and Make-based. It does not produce a package-managed target rootfs by default in the same way Yocto does.

## When To Use Buildroot

Buildroot is a good fit for:

- small systems
- quick prototypes
- rescue or manufacturing images
- single-purpose appliances
- products without complex package feeds
- learning embedded rootfs mechanics

Yocto/OE is usually stronger for:

- large distributions
- many product variants
- binary package feeds
- SDK generation
- complex license/SBOM workflows
- extensive layer reuse

## External Trees

Product work should use a `BR2_EXTERNAL` tree rather than editing Buildroot itself:

```text
br2-external-company/
  Config.in
  external.mk
  configs/product_defconfig
  board/company/product/
  package/company-agent/
```

This mirrors the same principle as Yocto product layers: vendor/upstream build logic remains replaceable.

## Common Tasks

```bash
make product_defconfig
make menuconfig
make
make savedefconfig
```

Important outputs usually appear under `output/images/`.

## Common Mistakes

- editing generated files under `output/`
- treating `menuconfig` changes as saved before running `savedefconfig`
- putting product changes directly in upstream Buildroot
- expecting target package management by default
- using rootfs overlays for files that should be generated by packages

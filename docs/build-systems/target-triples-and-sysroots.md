# Target Triples and Sysroots

## What Problem Does This Solve?

Target triples and sysroots describe what kind of system you are building for and where the target headers and libraries live. Without these concepts, cross-compilation becomes guesswork.

For embedded Linux, most difficult build failures eventually reduce to one question: did the build use the correct target environment?

## Core Concepts

- target triple
- architecture
- vendor field
- operating system field
- ABI
- C library
- hard-float vs soft-float ABI
- sysroot
- staging sysroot
- deployed root filesystem

## Mental Model

A target triple names a toolchain's target family:

```text
architecture-vendor-operating_system-abi
```

Examples:

```text
arm-linux-gnueabihf
aarch64-linux-gnu
riscv64-linux-gnu
arm-none-eabi
```

A sysroot is a filesystem tree used during compilation:

```text
sysroot/
  usr/include/
  usr/lib/
  lib/
```

The compiler uses it as if it were the root of the target system for headers and libraries.

The target triple answers "what kind of binary is this toolchain meant to produce?" The sysroot answers "which target headers and libraries should this build see?"

Keep these related but separate:

```text
target triple -> architecture and ABI family
sysroot       -> concrete target development filesystem
rootfs        -> concrete runtime filesystem deployed to the board
```

A correct triple with the wrong sysroot is still a broken build environment.

## Syntax / API / Mechanism

Show compiler target information:

```sh
arm-linux-gnueabihf-gcc -dumpmachine
arm-linux-gnueabihf-gcc -v
```

Compile with a sysroot:

```sh
arm-linux-gnueabihf-gcc \
  --sysroot=/opt/target-sysroot \
  main.c \
  -o app
```

Inspect default search paths:

```sh
arm-linux-gnueabihf-gcc -v main.c -o app
```

Inspect binary ABI:

```sh
readelf -h app
file app
```

Inspect program interpreter:

```sh
readelf -l app | grep interpreter
```

Inspect dynamic dependencies:

```sh
readelf -d app
```

Find the compiler's sysroot if configured:

```sh
arm-linux-gnueabihf-gcc --print-sysroot
```

## Minimal Example

```sh
aarch64-linux-gnu-gcc -dumpmachine
aarch64-linux-gnu-gcc --sysroot=/opt/aarch64-sysroot hello.c -o hello
file hello
readelf -h hello
```

Expected result: the output binary should report AArch64, not x86_64.

## Real-World Example

A TI Sitara workflow may have:

```text
SDK toolchain
SDK sysroot
target root filesystem
deployed board image
```

The safest path is to use the sysroot generated by the same SDK or build framework that produced the root filesystem. Mixing a newer sysroot with an older deployed image can build successfully but fail at runtime.

For example:

```text
TI Processor SDK release A
  -> compiler A
  -> sysroot A
  -> rootfs A

TI Processor SDK release B
  -> compiler B
  -> sysroot B
  -> rootfs B
```

Avoid compiler A plus sysroot B plus rootfs A unless you are intentionally porting and understand the compatibility surface.

## Common Scenarios

### `arm-none-eabi` vs `arm-linux-gnueabihf`

Use `arm-none-eabi` for bare-metal firmware. Use `arm-linux-gnueabihf` for 32-bit ARM Linux userspace with the hard-float ABI.

The difference is not cosmetic. The runtime startup files, system calls, C library assumptions, and ABI expectations differ.

If you see errors about missing `_exit`, system calls, or startup files while building a Linux userspace app, check whether a bare-metal toolchain was used by mistake.

### Hard-Float vs Soft-Float

For 32-bit ARM, ABI mismatches can be painful. `gnueabihf` indicates a hard-float ABI. If libraries and objects disagree on float ABI, link or runtime failures can result.

Inspect ARM attributes:

```sh
readelf -A app
```

This can show ABI attributes such as VFP usage on 32-bit ARM.

### Sysroot Does Not Match Runtime Rootfs

The build may link against `libfoo.so.3`, while the target only has `libfoo.so.2`. The compiler did its job; the release process used inconsistent inputs.

Check needed libraries:

```sh
readelf -d app | grep NEEDED
```

Then check the target root filesystem:

```sh
find rootfs -name 'libfoo.so*'
```

### SDK Sysroot vs Rootfs Copy

A sysroot is often cleaned and arranged for compilation. A root filesystem is arranged for runtime. They overlap, but they are not always identical.

Examples:

- a sysroot has headers; a minimal runtime rootfs may not
- a sysroot has unstripped libraries or linker symlinks; a runtime image may not
- a rootfs has configuration files, services, and device nodes; a sysroot may not

### glibc vs musl vs uClibc

The C library is part of the ABI contract. A binary built for a glibc sysroot generally does not run on a musl root filesystem. Buildroot systems may use different C libraries depending on configuration.

### Dynamic Linker Path

Dynamic executables record an interpreter path:

```sh
readelf -l app | grep interpreter
```

If the target does not contain that path, execution fails even if the CPU architecture is correct.

### Creating A Sysroot From A Target Rootfs

For experiments, developers sometimes copy headers and libraries from a target rootfs. This can work for quick tests, but it is fragile:

- symlinks must be preserved
- development headers may be missing
- linker symlinks may be missing
- library versions may not match source headers
- generated files may be absent

Prefer SDK-generated sysroots for serious work.

### Multiarch Library Directories

Some sysroots store libraries in paths such as:

```text
usr/lib/arm-linux-gnueabihf/
usr/lib/aarch64-linux-gnu/
```

Do not assume every target sysroot uses only `usr/lib`.

## Common Mistakes

- Treating all ARM toolchains as equivalent.
- Assuming a sysroot is optional for dependency-heavy target builds.
- Mixing sysroots from different SDK releases.
- Manually adding host `/usr/include` or `/usr/lib`.
- Forgetting that the dynamic linker path is embedded into dynamic executables.
- Copying target rootfs files into a sysroot without preserving symlinks.
- Treating the sysroot as a deployment image.
- Building against a sysroot with headers newer than the runtime libraries.
- Ignoring libc family differences.
- Assuming `--sysroot` fixes every manually supplied absolute path.

## Debugging Checklist

- Run `<compiler> -dumpmachine`.
- Run `<compiler> -v` and inspect configured target and search paths.
- Check `--sysroot`.
- Check `file app`.
- Check `readelf -h app`.
- Check `readelf -l app` for the program interpreter.
- Check `readelf -d app` for runtime library requirements.
- Compare the sysroot libraries with the deployed target libraries.
- Run `readelf -A app` for 32-bit ARM ABI details.
- Check the target rootfs for the program interpreter path.
- Check symlinks in the sysroot if libraries are not found.
- Check whether the build framework generated an SDK sysroot you should use instead of a hand-made one.

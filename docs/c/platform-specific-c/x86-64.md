# x86-64

x86-64 is a useful platform for learning ABI and generated-code reasoning because it
supports rich operating systems, multiple instruction extensions, and more than one
major calling convention. It is also a reminder that apparently simple C properties—
alignment, ordering, atomicity, executable memory, and stack layout—depend on the
execution environment rather than on the processor name alone.

## Learning Objectives

- Explain the System V AMD64 and Windows x64 calling-convention differences.
- Inspect stack alignment, saved registers, red-zone use, and return-value handling.
- Relate compiler options and CPU feature detection to generated scalar/SIMD code.
- Understand unaligned access, memory ordering, atomics, and user/kernel boundaries.
- Use ELF/PE metadata, disassembly, and debugger state to diagnose ABI failures.

## System V AMD64 Calling Convention

The System V AMD64 ABI commonly used by Unix-like systems classifies arguments and
passes integer or pointer values in `RDI`, `RSI`, `RDX`, `RCX`, `R8`, and `R9`; floating
and vector values use the XMM register convention. Additional or memory-classified
arguments are placed on the stack. Scalar return values normally use `RAX` (and
possibly `RDX`), while vector returns use SIMD registers.

The ABI also defines callee-saved registers, aggregate classification, variadic
function rules, structure return handling, and stack alignment. At a call boundary the
stack alignment requirement must be met; a compiler-generated prologue may subtract a
different amount depending on the saved registers and local objects.

The System V user-space ABI includes a 128-byte red zone below the stack pointer that a
leaf function may use without adjusting `RSP`. This is valid only where the execution
environment preserves it. Kernel code, interrupt contexts, signal/exception entry,
and mixed ABI code may not. Compile kernel or interrupt-sensitive code with the
platform-required red-zone setting disabled.

## Windows x64 Differences

Windows x64 uses a different register assignment and requires caller-provided “shadow
space” for callees. It also uses unwind metadata with rules that constrain prologues
and epilogues. A function pointer or object file built for one ABI is not automatically
compatible with the other, even though both execute x86-64 instructions.

At a C boundary, make the ABI explicit through the compiler target, calling-convention
attributes where supported, and a matching header. Be especially careful with:

- variadic functions and floating-point arguments;
- structure return and aggregate layout;
- exception/unwind metadata when interoperating with other languages;
- name decoration and import/export rules in PE/COFF;
- stack alignment and shadow/red-zone assumptions in assembly wrappers.

## Calling-Convention Inspection

Use a small, deterministic function and inspect it at the exact optimization settings
used in the product:

```c
#include <stdint.h>

struct pair {
    uint64_t first;
    uint64_t second;
};

struct pair add_pair(struct pair left, struct pair right)
{
    return (struct pair){
        .first = left.first + right.first,
        .second = left.second + right.second,
    };
}
```

Annotate where each field arrives, which registers are preserved, how the result is
returned, and whether optimization removes the stack frame. Repeat with a variadic
function, a floating-point parameter, and a large aggregate. This exercise is more
reliable than memorizing a simplified register list.

## Linux System Calls And The ABI Boundary

The Linux x86-64 syscall ABI is distinct from the System V C function ABI. The syscall
number is placed in `RAX`; arguments use `RDI`, `RSI`, `RDX`, `R10`, `R8`, and `R9`; and
the `syscall` instruction clobbers registers including `RCX` and `R11`. Normally libc
owns this boundary, handles restart/error conventions, and provides a stable C API.

If a freestanding runtime or a performance-critical wrapper invokes syscalls directly,
keep the assembly in one audited interface and document clobbers, errno behavior,
signals, cancellation, and architecture-specific error ranges. A direct syscall is
not automatically portable across operating systems, kernels, or ABIs.

## Unaligned Access And Object Representation

x86-64 hardware often handles ordinary unaligned loads, but that does not make every C
unaligned access correct. The pointer must still be valid and suitably aligned for its
declared type under the implementation. Use `memcpy` or an explicitly packed/byte-wise
representation for wire formats, and measure the cost when alignment matters.

Packed structures can generate multiple byte accesses, fault on a different target,
produce inefficient code, or violate a device's required access width. Separate the
wire representation from the native representation and convert at the boundary.

## Memory Ordering And Atomics

x86-64 has relatively strong ordering for ordinary memory, but C11 data races remain
undefined behavior and compiler reordering still matters. Use C atomics or OS locking
primitives for shared state. Do not infer correctness from a test that happens to pass
on x86 when the same code will run on Arm or RISC-V.

Atomicity also depends on size and alignment. Some naturally aligned operations are
atomic on the target, but a C implementation's lock-free guarantees are exposed by
`ATOMIC_*_LOCK_FREE` and `atomic_is_lock_free`, not by wishful assumptions. Atomics on
MMIO are a separate hardware question and should use device-specific accessors.

## SIMD And CPU Feature Selection

SSE, AVX, AVX2, AVX-512, and other extensions affect the available intrinsics, ABI
state, register-save cost, and operating-system support. A binary containing an
unsupported instruction fails at runtime even if it compiled successfully.

Common deployment strategies are:

- compile for a conservative baseline;
- dispatch to optimized implementations after a reliable CPU-feature query;
- let the deployment environment guarantee a minimum feature set;
- use compiler multiversioning only when its ABI, loader, and toolchain behavior are
  part of the product contract.

Keep feature-specific code behind a narrow API. Test the baseline path in CI; do not
let the build machine's CPU silently define the product's minimum requirement.

## ELF, PE/COFF, And Generated Code

ELF systems use relocations, symbol visibility, PLT/GOT mechanisms, TLS models, and
unwind/debug sections whose details affect dynamic linking and startup. Windows PE/COFF
uses different import/export, section, relocation, and unwind conventions. Inspect:

- symbol binding and visibility;
- relocation types and whether text relocations remain;
- section alignment and executable/write permissions;
- stack-unwind metadata;
- TLS model and per-thread storage;
- control-flow protection or other hardening notes.

Tools such as `objdump`, `readelf`, `nm`, `llvm-objdump`, and platform debuggers are
part of the C engineer's toolbox. Compare the map and disassembly with the source
when an ABI, startup, or optimization issue is suspected.

## Kernel And Interrupt Contexts

User-space assumptions do not transfer to kernels. A kernel may prohibit the red zone,
use a different page-table or address-space model, restrict floating-point/SIMD use in
some contexts, and require special atomic, preemption, or locking primitives. An
interrupt handler cannot assume it may call libc, allocate, sleep, or access a user
pointer without validation and fault-handling rules.

## Exercises And Diagnostics

1. Compile the same API for System V and Windows targets and compare argument registers,
   shadow space, unwind metadata, and aggregate returns.
2. Write a packed wire-format decoder using `memcpy`; compare it with a cast-based
   version and inspect alignment warnings and assembly.
3. Implement baseline and SIMD versions of a bounded operation, add runtime dispatch,
   and test the baseline on a machine without the optional feature.
4. Disassemble a variadic function and explain register-save areas and `va_list` layout
   for the selected ABI.
5. Capture a crash with symbols and without symbols, then practice recovering the call
   chain from unwind metadata and frame pointers.

## Common Mistakes

- Assuming all x86-64 systems use the System V ABI.
- Using the red zone in kernel, interrupt, signal, or mixed-runtime code.
- Treating hardware-tolerated unaligned access as a portable C technique.
- Shipping instructions newer than the deployment baseline.
- Assuming x86's ordering behavior proves a data-racy algorithm is correct.
- Calling a syscall with the C function ABI register order.
- Ignoring unwind, TLS, relocation, or executable-memory metadata when integrating
  hand-written assembly or a foreign-language component.

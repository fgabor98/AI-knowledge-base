# Learning Workflow And Tooling

Learning C effectively requires more than reading syntax. You need a repeatable loop that connects source code, compiler diagnostics, object files, runtime behavior, tests, and target hardware.

The most useful workflow is evidence-driven:

1. State one question.
2. Reduce it to the smallest useful program.
3. Compile with explicit options.
4. Inspect the diagnostic or generated artifact.
5. Run the smallest test.
6. Change one assumption.
7. Record what is guaranteed and what is implementation-specific.

## The Toolchain As A System

A C toolchain is a collection of cooperating components.

| Component | Responsibility | Evidence it produces |
|---|---|---|
| Preprocessor | Includes headers and expands macros | preprocessed source |
| Compiler | Parses, checks, optimizes, and generates code | diagnostics, assembly, object code |
| Assembler | Converts assembly to object code | relocatable object |
| Linker | Resolves symbols and places sections | executable, library, map file |
| C library | Supplies standard interfaces and runtime behavior | headers, libraries, symbols |
| Compiler runtime | Supplies helper operations generated by the compiler | runtime objects and libraries |
| Debugger | Controls and observes execution | breakpoints, registers, backtraces |
| Binary utilities | Inspect files and symbols | readelf, objdump, nm, size |
| Build system | Records dependencies and commands | build graph and command log |
| Test framework | Executes checks and records results | test results and reports |
| Static analyzer | Finds patterns without normal execution | findings and reports |
| Target tools | Flash, reset, trace, and observe hardware | images, logs, traces, register dumps |

A senior C developer is expected to move between these views. When a source-level explanation is insufficient, inspect the object file, linker map, disassembly, runtime trace, or hardware state.

## Start With A Host Build

Host builds are usually the fastest environment for learning:

- no board flashing
- fast rebuilds
- rich debuggers
- sanitizers
- fuzzing
- filesystem and process observability
- easy test automation

A minimal source file:

~~~c
#include <stdio.h>

int main(void)
{
    puts("C workflow probe");
    return 0;
}
~~~

Compile it with an explicit dialect and warnings:

~~~sh
cc -std=c17 -Wall -Wextra -Wpedantic -g -O0 probe.c -o probe
./probe
~~~

The exact compiler may be GCC, Clang, or a vendor compiler. Use the compiler actually selected by the project rather than assuming that cc means GCC.

Record:

- compiler identity and version
- selected language mode
- target triple
- warning options
- optimization level
- linked libraries
- build directory
- source revision

## Inspect The Compilation Stages

The compiler driver can expose intermediate stages. Common options include:

~~~sh
cc -std=c17 -E probe.c -o probe.i
cc -std=c17 -S probe.c -o probe.s
cc -std=c17 -c probe.c -o probe.o
cc probe.o -o probe
~~~

These outputs answer different questions:

- preprocessed source: which macros and headers reached the compiler?
- assembly: what instructions and calls did the compiler generate?
- object file: which symbols, sections, and relocations exist?
- linked executable: which runtime and libraries are present?
- running process: what does the program actually do?

For GCC, -### or -v can show the commands the driver would execute or the tools it invokes. Use this when diagnosing unexpected startup files, include paths, library paths, or target options.

The future [Compilation, Linking, And ABI](../compilation-linking-and-abi/index.md) chapter expands this workflow in detail.

## Build A Warning Baseline

Warnings are not a replacement for tests or static analysis, but they make assumptions visible earlier.

A portable starting point might include:

~~~sh
cc -std=c17 \
   -Wall -Wextra -Wpedantic \
   -Wformat=2 -Wshadow \
   -Wconversion -Wsign-conversion \
   -Wstrict-prototypes -Wmissing-prototypes \
   -Wundef \
   -g -O0 \
   probe.c -o probe
~~~

Do not copy this blindly into every project:

- some options differ between GCC and Clang
- vendor compilers may not support the same warnings
- legacy code may require an incremental warning migration
- generated code may need a separate warning policy
- kernel and RTOS projects often have their own required flags
- -Werror can turn an intentional migration into an unusable build

A mature project records:

- which warnings are enabled
- which are errors
- which are suppressed
- why each suppression exists
- which generated files are exempt
- how warning debt is reduced

## Use A Small Diagnostic Program

A diagnostic program can report the implementation environment:

~~~c
#include <stdio.h>

int main(void)
{
    printf("compiler: %s\n",
#if defined(__clang__)
           "Clang"
#elif defined(__GNUC__)
           "GCC-compatible"
#elif defined(_MSC_VER)
           "MSVC-compatible"
#else
           "unknown"
#endif
    );

#if defined(__STDC_VERSION__)
    printf("C standard macro: %ld\n", (long)__STDC_VERSION__);
#else
    puts("C standard macro: unavailable");
#endif

#if defined(__STDC_HOSTED__)
    printf("hosted: %d\n", __STDC_HOSTED__);
#else
    puts("hosted macro: unavailable");
#endif

    return 0;
}
~~~

This is diagnostic code, not a portable application technique. Compiler identification macros are useful for narrow compatibility adapters, but scattering them throughout application logic creates a portability burden.

## Debug With GDB

A basic GDB workflow:

~~~sh
gdb ./probe
~~~

Useful commands:

~~~text
break main
run
next
step
print variable
display variable
info locals
backtrace
frame 1
list
x/16bx address
disassemble /m function
continue
quit
~~~

Use breakpoints to stop at a known transition. Use watchpoints when a value changes unexpectedly. Use backtraces to identify the call path, not just the line where the program finally failed.

For embedded targets, the same reasoning applies through a remote debug connection:

- connect to the target
- reset and halt
- set a breakpoint
- inspect registers and memory
- continue to the fault
- capture the program counter and stack
- correlate addresses with the ELF and map file

The [GDB manual](https://sourceware.org/gdb/current/onlinedocs/gdb.html) is the primary reference for debugger behavior.

## Use Sanitizers On The Host

Sanitizers are most useful when the host build preserves the same logical behavior as the target component.

Sanitizers for address and undefined behavior:

~~~sh
cc -std=c17 -g -O1 \
   -fsanitize=address,undefined \
   -fno-omit-frame-pointer \
   test.c -o test
./test
~~~

ThreadSanitizer is a separate experiment:

~~~sh
cc -std=c17 -g -O1 \
   -fsanitize=thread \
   test_threads.c -o test_threads
./test_threads
~~~

Sanitizers can expose:

- out-of-bounds access
- use-after-free
- double free
- invalid shifts
- signed overflow
- invalid casts in some cases
- data races
- leaks

They do not prove that code is correct, and they do not reproduce all target behavior. They also may not be available for the target architecture or compatible with interrupt and MMIO code. Keep hardware access behind adapters so the logic can be instrumented on the host.

## Test In Small Layers

Use several test layers:

### Unit tests

Test a function or module with controlled inputs.

Good unit tests cover:

- normal values
- boundary values
- empty values
- maximum sizes
- invalid inputs
- repeated calls
- allocation failure
- timeout and retry behavior
- state transitions

### Integration tests

Test real module boundaries:

- parser plus transport
- driver plus mock hardware
- service plus configuration
- library plus target libc
- RTOS task plus queue

### Target tests

Test behavior that depends on:

- registers
- interrupts
- DMA
- cache
- timing
- power
- reset
- flash
- bootloader handoff

### Hardware-in-the-loop tests

Use hardware-in-the-loop for:

- board bring-up
- peripheral smoke tests
- power-cycle behavior
- firmware updates
- watchdog recovery
- manufacturing tests
- long-duration reliability

The test level should match the assumption being tested.

## Cross-Compilation Workflow

A cross build should make the target explicit.

Typical variables include:

~~~sh
TARGET=arm-none-eabi
CC=${TARGET}-gcc
OBJCOPY=${TARGET}-objcopy
OBJDUMP=${TARGET}-objdump
SIZE=${TARGET}-size
~~~

Do not assume that these tools exist or that the target is correct. Verify:

~~~sh
${CC} --version
${CC} -dumpmachine
${CC} -print-sysroot
${CC} -v
~~~

A cross-build record should include:

- compiler and binutils versions
- target triple
- CPU and ISA flags
- floating-point ABI
- sysroot
- include paths
- library paths
- linker script
- startup objects
- C library
- post-link image conversion
- flashing command
- debug connection
- map-file and size reports

The existing [Build Systems](../../build-systems/index.md) material covers the broader build-system side. C-specific learning should focus on how the selected commands alter language, ABI, runtime, and target behavior.

## Learn By Producing Artifacts

Each learning exercise should produce something inspectable:

- source code
- compiler command
- warning output
- preprocessed file
- assembly
- object file
- linker map
- executable or firmware image
- test result
- debugger transcript
- sanitizer report
- target log
- measurement
- written assumption record

If an exercise only says “the program worked,” it is too weak for senior-level learning.

## Recommended First Experiments

### Experiment 1: Hosted hello and inspection

- compile a small program
- inspect the preprocessed source
- emit assembly
- inspect symbols
- debug main
- run it under a sanitizer build

### Experiment 2: Warning exploration

Write small programs that contain:

- an implicit conversion
- a missing prototype
- an unused result
- a format mismatch
- an unreachable branch
- a signed/unsigned comparison

Compile with one additional warning at a time. Record:

- the diagnostic
- whether the program is valid ISO C
- the safer correction
- whether the correction changes the API

### Experiment 3: Object and linker inspection

- compile two source files
- call a function across the translation-unit boundary
- inspect symbols with nm
- inspect sections with readelf
- inspect relocations
- link a final executable
- compare the map and size report

### Experiment 4: Host model of an embedded component

Implement a small:

- ring buffer
- protocol parser
- state machine
- fixed-size allocator
- sensor conversion function

Then add:

- unit tests
- invalid-input tests
- sanitizer builds
- fuzz or property tests
- a narrow platform adapter

### Experiment 5: Target bring-up

When hardware is available:

- compile the smallest image
- confirm reset entry
- blink or toggle a GPIO
- send one diagnostic message
- inspect the map file
- halt in the debugger
- trigger and document one controlled fault

## Reading Documentation In The Right Order

Use the source that owns the question:

| Question | First source |
|---|---|
| What does ISO C guarantee? | ISO standard or WG14 public draft |
| Which language mode does the compiler accept? | Compiler manual |
| Why was an extension generated? | Compiler and target documentation |
| Which symbol is missing? | Linker output, map file, object inspection |
| What does a system call do? | POSIX and operating-system manual |
| What does a register mean? | Processor or vendor reference manual |
| What does a kernel API require? | Kernel documentation and source |
| What does an RTOS call permit from an ISR? | RTOS documentation |
| What does the board bootloader expect? | Boot-flow and platform documentation |
| Why did production fail? | Logs, traces, artifacts, and exact release metadata |

Do not use a tutorial as the final authority for a standards or hardware question. Use tutorials to find the vocabulary, then verify the rule in the primary documentation.

## A Repeatable Investigation Template

~~~text
Question:
  What exact behavior am I trying to explain?

Minimal reproduction:
  What is the smallest source that shows it?

Environment:
  Compiler, version, dialect, target, ABI, libc, optimization.

Expected result:
  What does the language, implementation, or platform contract say?

Observed evidence:
  Diagnostics, preprocessed source, assembly, symbols, trace, registers.

Classification:
  ISO-defined, implementation-defined, extension, ABI, OS, hardware, or bug.

Action:
  Fix, document, isolate, test, or intentionally accept the dependency.

Regression:
  Which test or build check prevents recurrence?
~~~

## Common Mistakes

- Learning compiler commands without recording the language mode.
- Treating a successful host run as proof of target correctness.
- Using -O0 forever and never inspecting optimized behavior.
- Enabling -Werror without an incremental migration plan.
- Ignoring the preprocessor when debugging a header or macro issue.
- Debugging source lines without inspecting the final binary.
- Using sanitizers on only one build variant.
- Testing happy paths and omitting bounds, failure, timeout, and reset behavior.
- Treating a debugger transcript as a reproducible test.
- Not recording the exact compiler, linker, sysroot, and target options.
- Reading a vendor tutorial without checking the reference manual.
- Hiding the target adapter inside logic that should be host-testable.

## Orientation Completion Checklist

You are ready for the Language Fundamentals chapter when you can:

- describe the three contracts of a C project
- explain the difference between hosted and freestanding execution
- name the C standard edition and compiler dialect used by a project
- classify an assumption as language, implementation, ABI, OS, hardware, or product behavior
- compile and inspect a small C program
- read basic compiler diagnostics
- use GDB to stop, inspect, and backtrace
- run a host sanitizer build
- explain why host tests and target tests are both needed
- produce a reproducible record of a C experiment

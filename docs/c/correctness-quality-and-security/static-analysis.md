# Static Analysis

Static analysis examines source, an intermediate representation, or object metadata without executing the complete program. It can find defects across paths that tests do not cover, enforce project rules, and provide evidence for safety and security processes. It is not magic: results depend on the compilation model, annotations, configuration, assumptions about external functions, and the analyzer’s precision.

## Learning Objectives

- distinguish compiler diagnostics, linting, path-sensitive analysis, abstract interpretation, and formal proof;
- configure analysis with the same headers, macros, target flags, and generated files as the product build;
- interpret true positives, false positives, false negatives, and inconclusive results;
- manage baselines and suppressions without hiding new defects;
- apply MISRA/CERT and project-specific rules with traceable deviations;
- use analyzer output to improve code and tests rather than merely close warnings.

## Analysis Families

| Family | Strength | Limitation |
| --- | --- | --- |
| compiler warnings | fast local feedback, type and flow checks | limited interprocedural/path knowledge |
| lint/style | consistency and suspicious idioms | shallow model unless configured |
| path-sensitive analyzer | null, leak, lifetime, error-path exploration | path explosion and environment assumptions |
| abstract interpretation | ranges, alarms, value and memory properties | approximation and proof obligations |
| security scanner | known weakness patterns and taint flows | context and exploitability may be unclear |
| complexity/include tools | structural maintainability evidence | metric is not behavior correctness |
| formal deductive tool | properties under explicit model | specification and proof cost |

Use multiple families. A compiler warning about a conversion, a taint finding about an input path, and a range analyzer alarm about an index describe different risks.

## Analyze The Product Build

The analyzer must see the same effective program as the compiler:

- target and ABI flags;
- language standard and extensions;
- include search paths and generated headers;
- conditional macros;
- linker-provided symbols and section attributes where modeled;
- RTOS or OS APIs and annotations;
- source files excluded or generated by the build;
- third-party code and its approved boundaries.

For Clang-based tooling, compile commands are commonly supplied through `compile_commands.json`. For GCC’s analyzer:

~~~sh
gcc -std=c17 -Wall -Wextra -fanalyzer \
    -Iinclude -Igenerated -c src/packet.c
~~~

Run the analyzer in CI from the same build graph as the target. A separate hand-written command often analyzes the wrong configuration.

## Path-Sensitive Reasoning

Path-sensitive tools can model branches and function calls. This function has a path-dependent error:

~~~c
#include <stddef.h>
#include <string.h>

int copy_name(char *destination,
              size_t capacity,
              const char *source)
{
    size_t length;

    if (destination == NULL || source == NULL) {
        return -1;
    }
    length = strlen(source); /* Include <string.h> in production code. */
    if (length >= capacity) {
        return -2;
    }
    memcpy(destination, source, length + 1u);
    return 0;
}
~~~

The `capacity == 0` path is rejected indirectly when `length >= capacity`, which is correct here, but the analyzer may still need models for `strlen` and `memcpy`. In a complete file include `<string.h>` and use the project’s string policy. Do not silence a finding until the path, contract, and library model have been checked.

## Range And Abstract Interpretation

An abstract interpreter represents sets of possible values rather than executing one concrete value. It may prove that an index is within bounds, report a possible signed overflow, or emit an alarm because information is too imprecise. An alarm means “the analysis could not establish safety under its current model,” not necessarily “a failure definitely occurs.”

Improve precision by:

- adding preconditions and range checks;
- separating impossible states with enums or tagged types;
- constraining configuration inputs;
- providing summaries for hardware and RTOS functions;
- analyzing the correct call graph and entry points;
- avoiding global mutable state that hides dependencies;
- splitting complex functions when path explosion obscures the result.

Never “fix” an alarm by adding an arbitrary cast or suppression. Either strengthen the code, strengthen the proof/model, or document why the alarm is outside the supported environment.

## Security And Taint Analysis

Taint analysis follows data from untrusted sources to sensitive sinks. Sources may include radio packets, USB, network sockets, configuration files, bootloader metadata, or sensor input. Sinks may include memory copies, format strings, command interpreters, file paths, register writes, authorization decisions, or cryptographic operations.

The analyzer needs project-specific knowledge:

- which APIs validate lengths and encodings;
- which handles represent trusted versus untrusted data;
- which sanitizers canonicalize input;
- which functions cross a privilege or trust boundary;
- which logging paths can leak secrets.

A taint-clean result is meaningful only if sources and sinks are modeled completely.

## Rule Sets And Baselines

Adopt a rule set in stages:

1. establish compiler and analyzer versions;
2. run on representative code and classify findings;
3. fix high-confidence defects;
4. establish a reviewed baseline for legacy findings;
5. fail CI on new or worsened findings;
6. reduce the baseline deliberately;
7. review rule changes as engineering changes.

Store each suppression with:

- rule identifier and exact location;
- reason and risk assessment;
- compensating test, assertion, or review;
- owner and expiry/review date;
- tool/version context;
- whether the issue is a false positive, accepted implementation extension, or known debt.

Do not use a giant global suppression file to make a report green. A green report with no trustworthy signal is worse than an honest baseline.

## CERT And MISRA Analysis

CERT C emphasizes secure coding risks; MISRA C constrains language use for critical systems. Tool rule names and interpretations vary. Map a finding to the exact rule version, project configuration, and deviation process. A warning from a tool is evidence for review, not automatic proof of noncompliance or compliance.

For each required rule, define:

- applicability and scope;
- automated detection coverage;
- manual review method;
- permitted deviations;
- required rationale and approval;
- regression protection;
- evidence retention.

## Complexity And Structure

Metrics can identify review hotspots:

- cyclomatic or decision complexity;
- nesting depth;
- function and module size;
- fan-in/fan-out;
- coupling and include depth;
- churn and defect history;
- duplicated logic;
- unreachable or dead code.

Metrics should trigger a question, not an automatic rewrite. A small interrupt handler with complex hardware state can deserve more scrutiny than a larger generated table. Combine metrics with hazard, change, and defect data.

## False Positives And False Negatives

Classify findings by evidence:

- **true positive** — code violates a real contract or can fail;
- **false positive** — the analyzer’s model is too broad or misses a valid invariant;
- **configuration issue** — wrong target, headers, macro, entry point, or model;
- **accepted deviation** — risk is understood and controlled;
- **unknown** — insufficient evidence; investigate before closing.

Static analysis can miss defects due to unmodeled assembly, volatile hardware, concurrency, aliasing, integer ranges, generated code, external libraries, or infeasible paths. Combine it with tests and runtime evidence.

## Exercises

1. Run GCC `-fanalyzer` and a second analyzer on the same compile database.
2. Add a null, bounds, and error-path defect and verify each tool’s report.
3. Supply a model for a target allocator or RTOS API and compare results.
4. Create a baseline, add a new finding, and make CI fail only for the new issue.
5. Write and review a local suppression with an expiry and compensating test.
6. Measure include depth, complexity, and churn for a driver and decide where refactoring helps.
7. Map analyzer findings to CERT/MISRA rules and record manual coverage gaps.

## Common Mistakes

- analyzing a different configuration from the product build;
- treating every alarm as a confirmed bug or every warning as noise;
- suppressing by line range so a future defect disappears;
- ignoring external, assembly, RTOS, and hardware models;
- using a legacy baseline as permanent immunity;
- claiming MISRA or CERT compliance from one tool report;
- optimizing complexity metrics instead of reducing risk;
- failing to review analyzer upgrades and changed findings;
- omitting generated code and preprocessor configuration from evidence.

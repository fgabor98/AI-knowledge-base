# Userspace, Kernel, And Hardware Boundary

## What problem does this solve?

When a userspace program opens a device, reads a file, sends a packet, or waits for
an event, several layers participate. A useful diagnosis must identify which layer
accepted the request, which layer produced the error, and which layer’s behavior has
not yet been observed. This prevents two common mistakes: treating libc as if it
were the kernel, and treating a successful system call as proof that hardware
completed the requested action.

## A request, traced carefully

Consider:

```c
int fd = open("/dev/my_sensor", O_RDONLY | O_CLOEXEC);
ssize_t count = read(fd, sample, sizeof sample);
```

The possible path is:

1. The compiler translates the source and the linker records a reference to the
   libc `open` and `read` wrappers.
2. The dynamic loader maps the executable and its libraries before `main` runs.
3. The libc wrapper validates or prepares arguments and enters the kernel. Some libc
   functions, such as formatting into a caller-owned buffer, may never enter it.
4. The kernel checks the process credentials, pathname, mount namespace, and file
   permissions. VFS path resolution finds a device node and dispatches to the
   registered driver or subsystem.
5. The driver may configure hardware, submit a request, wait for an interrupt, read
   a buffer, or return a cached sample. The device may continue work after the
   system call returns.
6. The result crosses back as a return value and possibly `errno`. The program must
   interpret the documented result and own the resulting resource or data.

An ordinary `read` does not mean “the sensor physically performed a fresh
measurement.” It means that the file descriptor’s interface returned bytes according
to its contract. The subsystem may define whether those bytes are queued, cached,
sampled on demand, or generated by a different component.

## Privilege separation

User mode and kernel mode are protection domains, not separate computers. A process
normally cannot execute privileged instructions, access arbitrary physical addresses,
modify page tables, or touch another process’s memory. It requests controlled
operations through system calls and documented UAPIs.

The boundary provides:

- memory isolation between processes and between user and kernel mappings;
- permission and credential checks;
- a stable entry point for scheduling, memory, filesystem, networking, and device
  services;
- containment of many application faults to one process;
- a reviewable security boundary for device access and privileged operations.

It is not an absolute safety boundary. A kernel bug, a vulnerable driver, an
over-permissive device node, or a process with excessive capabilities can defeat the
intended policy. A userspace service should therefore ask for the narrowest UAPI and
run with the narrowest credentials that meet its job.

## What each layer owns

| Layer | Owns | Does not automatically guarantee |
| --- | --- | --- |
| Application | Protocol state, buffer sizes, retries, ownership, policy, and user-visible meaning | That a kernel request completed, that a path exists, or that a peer remains alive |
| libc | C/POSIX abstractions, wrappers, allocation policy, buffering, and thread-local `errno` implementation | A particular kernel version, device behavior, or target rootfs |
| Dynamic loader | Loading shared objects, relocations, symbol resolution; the kernel maps the requested interpreter | That a library has the expected configuration or ABI semantics |
| Kernel | Isolation, scheduling, virtual memory, VFS, sockets, credentials, and driver dispatch | That hardware is wired, powered, calibrated, or physically responsive |
| Driver/subsystem | The documented UAPI and translation to a device or protocol | That every board has the same wiring or that undocumented behavior is stable |
| Hardware/firmware | Electrical state, timing, conversion, storage, and device-specific behavior | That the caller handled timeouts, disconnects, bad data, or power loss |

The ownership column is also a debugging boundary. If `open()` returns `ENOENT`,
investigate path resolution, mounts, and rootfs contents before investigating the
sensor’s signal integrity. If `open()` succeeds but a later `ioctl()` returns
`ENODEV`, inspect driver binding, power, firmware, and device state.

## Observation has limits

`strace` records the process’s system-call boundary. For example, it can show:

```text
openat(AT_FDCWD, "/dev/my_sensor", O_RDONLY|O_CLOEXEC) = 3
read(3, ..., 32) = -1 EAGAIN (Resource temporarily unavailable)
```

That establishes the arguments, return value, and kernel-visible error. It does not
establish why a physical sensor had no sample. For deeper evidence, correlate:

- kernel logs (`dmesg` or the product’s journal policy);
- `/sys` state and uevents where the subsystem exposes them;
- driver-specific diagnostics and tracepoints;
- power, clock, bus, and firmware evidence;
- timestamps from the application and device;
- an oscilloscope, logic analyzer, or protocol analyzer when electrical behavior is
  in question.

Use the least invasive observation first. Enabling verbose driver tracing or changing
timing can alter a race, consume storage, or perturb a real-time system.

## UAPI is a contract, not a memory shortcut

The application may use a documented device node, sysfs attribute, `ioctl`, `poll`,
`mmap`, netlink protocol, or standard subsystem API. It must not infer a private
driver layout or cast a physical address into a pointer. Kernel memory and device
registers are not ordinary application objects.

For an `ioctl` or binary UAPI, review:

- command direction and size;
- integer widths and signedness;
- pointer representation and 32/64-bit compatibility;
- structure padding and reserved fields;
- versioning and feature discovery;
- ownership of buffers during the call and after it returns;
- whether the operation can block, be interrupted, or return partial state.

The kernel side must validate user data and access user memory according to the UAPI;
drivers commonly copy data into kernel-owned storage for the duration of an
operation. The application must initialize all fields required by the UAPI and treat
undocumented fields as unavailable.

## Minimal experiment

Build the chapter probe and trace it:

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -g \
    examples/c/linux-userspace-environment-and-mental-model.c \
    -o /tmp/environment-probe
strace -o /tmp/environment-probe.strace /tmp/environment-probe
```

Find the `openat`, `readlink`, `uname`, and `close` calls. Then compare the program’s
printed identity with `/proc/self/status` and `/proc/self/ns/*`. The experiment shows
the process boundary; it deliberately does not claim to model a device driver.

## Real-world failure classification

For a hardware-facing operation, classify the first failed boundary:

| Evidence | Likely boundary | Next question |
| --- | --- | --- |
| `execve` fails with `ENOENT` for an existing file | ELF interpreter or library deployment | What does `readelf -l` request, and is that path in the target rootfs? |
| `open()` returns `ENOENT` | Path, mount, rootfs, or device-node discovery | Is the expected filesystem mounted and has the device been enumerated? |
| `open()` returns `EACCES` | Credentials, mode bits, ACL, LSM, or service sandbox | Which UID/GIDs/capabilities and policy apply to the service? |
| `ioctl()` returns `ENOTTY` | Wrong file type or unsupported command | Is this the right subsystem UAPI and kernel configuration? |
| `ioctl()` returns `ENODEV` | Driver or hardware availability | Is the device bound, powered, and firmware-ready? |
| `read()` blocks | No data, flow control, driver wait, or wrong mode | What is the documented wakeup and timeout policy? |
| `read()` returns `EAGAIN` | Nonblocking operation has no data now | Is retry driven by readiness, a deadline, or a bounded polling policy? |
| `read()` returns bytes but values are invalid | Protocol, calibration, version, or hardware state | Are length, endianness, timestamp, range, and validity fields checked? |

Never “fix” a missing device by creating a regular file at `/dev/my_sensor`. That can
make an existence check pass while hiding the real enumeration or deployment error.

## Common mistakes

- Calling every library function a system call.
- Assuming `errno` describes hardware rather than the failed interface boundary.
- Treating `/dev`, `/sys`, or `/proc` as ordinary persistent storage.
- Using an undocumented `ioctl` layout or a private sysfs attribute.
- Treating `poll()` readiness as successful I/O or physical completion.
- Debugging application logic before checking the target rootfs, credentials, mounts,
  kernel configuration, and driver binding.
- Assuming a host device file has the same major/minor number, permissions, or
  semantics as a target device file.

## Debugging checklist

- Record the exact binary, arguments, environment, UID/GIDs, capabilities, and
  namespace membership.
- Capture the failing system call and its complete return value with `strace` where
  allowed.
- Check the target’s kernel release, configuration, logs, and subsystem state.
- Confirm the path, mount, device node, symlink target, and service sandbox.
- Separate “request accepted” from “operation completed” in the protocol and logs.
- Add timestamps and stable error context at the application boundary.
- Use a fixture or fake UAPI for application tests, then verify the real UAPI on the
  target.
